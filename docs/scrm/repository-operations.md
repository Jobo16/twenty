# 仓库运行方式

本仓库是独立 SCRM 产品的唯一源码和协作入口。它保留 Twenty 可复用的工程能力，但不再复用上游的产品宣传、组织账号、部署基础设施或自动化分发服务。

## 分支与责任

仓库只保留两个长期分支：

| 分支 | 用途 | 谁可以写入 |
| --- | --- | --- |
| `test` | 日常开发、共享验证和集成 | 负责人将已审查的共享改动提交并推送 |
| `main` | 已验证、可发布的稳定基线 | 负责人从已验证的 `test` 推进 |

所有 Agent 共同使用仓库根目录的 `test`，并通过[任务看板](task-management.md)认领和交付。内部工作不使用 GitHub Issue、PR、功能分支或 worktree。Agent 在共享目录中只编辑自己任务的文件范围、记录检查结果，默认不提交或推送；负责人或 Codex 负责审查、提交和分支推进。

根目录 README 只解释项目身份、快速开始和入口文档；产品架构、业务口径、部署设计和任务细节都放在 `docs/scrm/`。

## 共享目录保护规则

- 开始工作前确认当前分支为 `test`，并读取 `git status` 和任务看板；不能通过重置、清理或暂存来处理他人的改动。
- 不新建、切换或删除分支和 worktree；不强制推送，不重写共享历史。
- 任务必须有互不重叠的文件边界。共享入口、根配置、迁移和公共测试夹具只由看板中明确的集成任务修改。
- `main` 不承载未验收工作。推进前应完成受影响范围的检查，并确认共享目录没有其他待验收改动。

详细的代码边界、验证和数据安全规则见[开发规范](development-standards.md)。

## 自动化边界

保留与本仓库直接相关的构建、测试、文档和 SCRM 域校验。继承自 Twenty、会向 `twentyhq` 组织、`twenty-factory`、`twenty-infra`、`ci-public` 或上游通知地址发起调用的工作流不属于本项目的交付链路，应从仓库移除而不是在本仓库中静默失败。

部署、预览环境、翻译同步、视觉回归和 AI 审查只能在拥有本项目自己的凭据、目标环境、责任人和失败处理方式后引入。不得复用或猜测上游密钥。

## GitHub 配置基线

代码中的 `CODEOWNERS` 仅声明审查归属。仓库管理员应限制 `main` 的强制推送和删除，并保留 SCRM 域的类型检查、单元测试和 lint。内部协作不要求以 PR 作为分支推进条件；`test` 到 `main` 的验收由负责人执行。

启用私密漏洞报告和秘密扫描推送保护。不要在仓库、文档、任务记录或自动化配置中记录令牌、密钥、客户数据或生产地址。

## 部署边界

本地、测试和生产的运行方式见[部署拓扑与发布流程](deployment.md)。生产配置、受管服务凭据和正式发布由环境负责人维护；源码仓库只保存无密钥的模板、部署定义和可复现的发布步骤。

## 来源与许可

上游代码选择、人工挑选和许可证边界见[上游代码使用策略](upstream-policy.md)。保留原始 `LICENSE`、第三方许可证和适用的版权声明；删除上游产品文案或工作流不改变这些义务。
