# 目标架构

## 分层

```text
产品界面
销售工作台｜企微侧边栏｜管理驾驶舱｜平台运营后台
                         ↓
应用服务
客户统一｜派发领取｜任务 SOP｜企微同步｜漏斗报表
                         ↓
领域内核
身份｜归属历史｜来源触点｜生命周期事件｜任务状态机
                         ↓
基础设施
Workspace 数据｜PostgreSQL｜Redis/BullMQ｜对象存储｜企微 API
```

领域内核不依赖界面、数据库和外部平台。应用服务负责权限、事务、幂等和调用编排；适配器负责 Twenty 现有存储、企微协议和外部服务。

## 多租户

一家客户企业对应一个 Workspace。Twenty 当前为每个 Workspace 创建独立 PostgreSQL schema，这可以继续作为第一层数据隔离。

数据库之外的资源必须显式隔离：

- Redis 锁和缓存键必须包含 Workspace ID。
- 队列任务必须携带 Workspace ID、连接 ID、幂等键和重试信息。
- 对象存储使用 `workspace/<workspaceId>/...` 路径并在下载时重新鉴权。
- 企微回调先由可信的 CorpID/Suite 授权关系解析 Workspace，不能相信客户端传入租户。
- 平台运营跨租户操作单独授权并记录原因和审计。

## 核心业务模型

### 客户与身份

客户主体描述“这个人或业务主体是谁”；客户身份描述“他通过哪个系统或账号出现”。企微 `external_userid` 只是身份之一。

身份唯一性以 Workspace、企微连接、身份类型和外部 ID 共同确定。客户合并必须保留原身份、来源和审计，不能直接修改外部 ID 指向后删除历史。

### 客户归属

当前负责人是查询投影，归属记录是事实。一次转移必须在同一事务内：

1. 锁定客户和当前有效归属。
2. 结束旧归属。
3. 创建新归属。
4. 更新客户当前负责人投影。
5. 追加 `ASSIGNED` 生命周期事件和 outbox 事件。

调用者只提交“把客户在某时刻转给谁以及原因”，不自行拼装这些步骤。

### 来源与漏斗

来源触点和生命周期事件只追加，并保存事件发生时的负责人、团队、渠道和活码稳定 ID 及名称快照。报表事实只能从这些事件生成，不允许连接客户、成员、渠道或活码的当前字段补历史维度。漏斗按事件统计，不根据客户今天的字段反推历史。

销售、渠道或活码改名时，稳定 ID 保证同一维度仍可聚合，名称快照保证历史展示不漂移；客户转移不搬走过去业绩。新增销售、渠道和活码只影响新增事件，不会改写旧周期。修正已发布周期需要创建可审计的修订版本。

### 销售任务

任务是一等业务对象，支持待领取、已领取、处理中、完成和取消。派发、转派、拒绝、超时和完成均形成状态历史。外部通知发送前重新验证客户、负责人和任务仍然有效。

## 权限

权限由四个维度共同决定：功能权限、组织数据范围、字段敏感度和动作条件。

销售默认只能访问本人负责的客户和任务；组长访问小组；部门负责人访问部门；租户管理员管理本企业；平台运维不自动获得业务数据权限。

权限判断集中在服务端策略层，前端菜单和按钮只反映服务端结果，不构成安全边界。

## 模块边界

| 模块 | 拥有的知识 |
| --- | --- |
| `scrm-domain` | 状态机、历史事实、领域不变量 |
| `scrm-server` | 事务、权限、存储、outbox、任务编排 |
| `scrm-wecom` | 企微授权、签名、回调、API 限制、同步游标 |
| `scrm-analytics` | 事件口径、周期快照、漏斗和下钻 |
| `scrm-front` | 销售、管理者和平台运营的任务界面 |

这些是职责边界，不要求立即拆成五个独立部署服务。第一阶段保持模块化单体。
