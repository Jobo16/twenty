# 上游代码使用策略

`origin` 是产品仓库，`upstream` 仅用于比较和查阅 Twenty 官方变化。

不做定期合并，也不整树合并 `upstream/main`；不承诺兼容 Twenty App 或 Cloud 产品。上游变化按以下顺序评估：

1. 高危安全修复。
2. PostgreSQL、Redis、依赖和运行时兼容修复。
3. 我们仍在使用的元数据、视图和通用 UI 缺陷修复。
4. 明确降低自有维护成本的新能力。

吸收方式优先为理解修复后在当前架构重新实现；适合时才 cherry-pick。每次吸收记录来源提交、适用模块、许可证和回归结果。

不会因为上游新增抽象，就让 SCRM 领域模块迁移到该抽象。只有它能减少当前调用方的认知负担和变更放大时才采用。
