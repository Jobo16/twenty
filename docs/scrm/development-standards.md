# SCRM 开发规范

这些规则适用于这个仓库中新建或改造的 SCRM 代码。它们补充根目录的 [CLAUDE.md](../../CLAUDE.md)：同一主题以更严格的规则为准。代码应以清晰的业务边界和可验证的行为为目标，不能为了复用 Twenty 的旧结构或预留假设中的扩展而增加复杂度。

## 交付边界

- 日常开发只在共享的 `test` 分支和仓库根目录进行；`main` 只接收已验收、可发布的 `test` 修订。
- 每项任务先在[任务看板](task-management.md)标记“进行中 · 姓名”，并写明互不重叠的目录边界、排除项和验收命令。任务行是唯一认领锁。
- 提交不得混入格式化、依赖升级、翻译目录、生成文件或无关重构。负责人只将已审查的完整切片提交到 `test`。
- 交付记录写在任务行：行为变化、实际验证、数据库变更、配置项和未覆盖风险。Agent 默认不提交或推送共享目录中的改动。
- 在没有明确授权时，不推送、合并、发布、修改生产配置或使用真实企业微信凭据。

## 并行任务拆分

- 并行任务只能依赖已经合入 `main` 的代码、配置和文档，不能依赖另一个仍在开发或评审中的任务。发现此类依赖时，先把前置工作单独合入，再分发后续任务。
- 每个并行任务拥有明确且互不重叠的目录。共享的包入口、根配置、数据库迁移、公共测试夹具和跨模块文档由一个后续集成任务统一修改。
- 一个任务如需改动其他任务的目录或公共入口，停止扩展范围，在交付记录中说明所需接口；由负责人决定调整边界或新建集成任务。
- 优先按稳定边界拆分：领域子模块、企微适配层、读模型、界面或测试，而不是按同一流程的前后步骤拆分。
- 分发前先写明每个任务的基线 commit、文件所有权、输入和输出。审查时按任务自己的验收标准判断，不以其他并行任务是否完成作为前提。

## 共享 test 协作流程

- 同一时间只领取状态为“待办”的任务；领取人立即把任务行改为“进行中 · <姓名>”。如果已有领取人或文件范围重叠，停止编辑并标记为“阻塞”。
- Agent 不创建分支、worktree、Issue 或 PR，也不执行 `git checkout`、`git reset`、`git clean`、`git stash`、历史重写或强制推送。共享目录中出现其他人的改动时，只避开其范围。
- 任务需要公共入口、根配置、迁移、共享测试夹具或他人目录时，先记录所需接口和原因；负责人拆成一个明确的集成任务后才可修改。
- 完成后将任务改为“待验收”，写入检查结果和影响范围。负责人审查工作区，再以小而完整的提交推送 `test`；只有完整验收通过才推进 `main`。

## 模块与依赖

SCRM 采用“领域内核 + 应用服务 + 基础设施适配 + 读模型/界面”的分层。模块应隐藏内部细节，对外暴露小而稳定的操作和类型。

| 层 | 位置 | 可以依赖 | 不可以依赖 |
| --- | --- | --- | --- |
| 领域内核 | `packages/scrm-domain` | TypeScript 标准能力、极少量无运行时工具 | NestJS、React、TypeORM、数据库、HTTP、企业微信 SDK |
| 应用服务 | `packages/twenty-server/src/modules/scrm` | 领域内核、Twenty 服务端约定 | 前端状态、企微 SDK 的业务细节 |
| 基础设施适配 | `packages/twenty-server/src/modules/scrm/infrastructure` | 应用服务端口、TypeORM、Redis、队列、企微 SDK | 绕过领域规则直接实现业务决定 |
| 查询与界面 | `packages/twenty-server/src/modules/scrm/read-models`、`packages/twenty-front/src/modules/scrm` | 面向用例的读模型和 API | 直接改写业务聚合、依赖数据库内部结构 |

- 依赖只能由外层指向内层。领域内核通过端口表达存储、时钟、消息、加密或企微能力，由外层实现。
- 不在 `twenty-shared` 放置仅属于 SCRM 的类型或工具；不为了复用而污染通用模块。
- 模块之间传递稳定的命令、查询和结果类型，不能跨模块读取彼此的 ORM Entity 或私有表结构。
- 使用 TypeScript 类型、命名导出、字符串字面量和现有仓库工具；其余代码风格遵从 `CLAUDE.md` 和相邻模块。

## 多租户、身份与权限

- 每个 SCRM 业务资源、事件、缓存键、队列消息和对象存储路径都必须带 tenant/workspace 归属。外部企业标识只能在其租户映射被验证后进入业务流程。
- 所有写入由服务端从认证上下文得到操作者和 tenant，不能信任前端、侧边栏参数或回调载荷声称的权限。
- 权限判定同时检查能力和数据范围：本人、团队或全租户。被保护资源的 tenant、归属人和团队必须作为判定输入。
- 外部身份（企微、手机号、邮箱、业务系统 ID）使用来源和租户限定的键；合并客户时保留冲突和审计结果，禁止跨租户合并。

## 事实、归属与报表

- 当前客户资料只表示现在；历史事实只追加，不能为修正当前字段而回写。
- 每次阶段、归属、来源、话码或关键关系变化，必须产生可追溯的生命周期事件。事件保留稳定 ID 和显示名称快照。
- 漏斗和销售报表从事件事实聚合，不能通过当前客户的销售、渠道或话码重新解释过去的周期。
- 新增、改名或停用渠道、成员、团队和话码不会改写旧事实。统计口径、去重键、周期时区和重复事件的处理规则必须写入代码测试和相关文档。

## 企业微信集成

- 企业微信接入分为连接管理、回调验签/解密、事件标准化、应用服务处理和异步投递。各层不得混合。
- 回调在映射至唯一 tenant、完成签名/解密校验并获得幂等键之前，不得创建或更新 SCRM 业务数据。
- 使用持久化的幂等记录和 outbox/可靠投递机制处理重复回调与下游失败；禁止以进程内内存当作唯一去重手段。
- 侧边栏会话必须绑定 tenant、操作者、外部身份和解析出的客户。上下文不完整、过期或冲突时，只能要求重新解析，不能执行写入。
- 密钥仅由环境配置或受管密钥服务提供；不得写入代码、测试夹具、日志、任务记录或错误消息。

## 数据库、API 与界面

- 需要持久化时，先定义领域操作和事务边界，再创建 Entity、迁移和 repository。一次业务动作产生的当前状态和事实事件必须在同一事务中成功或失败。
- 服务端 Entity 变化遵从 Twenty 的迁移命令和升级命令规则；迁移需要可审查的 `up` 与 `down`，不得手改已提交的迁移历史。
- API 面向销售、管理者和企微侧边栏的具体用例设计，返回读模型而不是泄露 Entity。写操作使用明确命令，并返回可显示的业务错误。
- 前端不承担租户隔离、权限或幂等的最终保证。用户可见文案走 Lingui；优先复用 Twenty UI、图标和可访问性模式。

## 测试、可观测性与隐私

- 领域规则必须有快速单元测试，覆盖允许与拒绝路径、跨租户、重复事件、状态转换和历史快照。测试行为，避免只验证内部实现。
- 应用服务补充事务、权限和 adapter 集成测试；涉及企微回调时覆盖验签失败、未知企业、重复 delivery 和重放。
- 每项改动至少运行受影响包的类型检查、测试和 lint；无法运行时，在交付中说明原因及未验证范围。
- 每个异步命令、回调和事实事件都记录可关联的事件 ID、tenant ID 和结果状态。日志、追踪和错误信息不得输出客户正文、令牌、手机号等敏感内容。
- 会话存档和 AI 结论必须有可验证的证据引用与访问范围。AI 输出不能绕过同一 tenant 的数据权限或展示不可访问的原文。

## 文档与决策

- 影响模块边界、数据口径、租户模型、企业微信协议或隐私策略的决定，新增 ADR 或更新对应架构文档。
- 为未完成功能在任务看板或开发待办中留下具体后续项，不用模糊 TODO 代替产品决策。
- 只有确认属于 SCRM 的上游修复才可挑选或重新实现；禁止例行合并 Twenty 上游。详见 [上游代码使用策略](upstream-policy.md)。
